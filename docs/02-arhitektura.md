# Архитектура и план развития

## Общая схема

```
┌──────────────────────────────┐        ┌──────────────────────────────┐
│            R-Pro             │        │      Агент (Python 3)        │
│  (.NET 4.5, WPF, Python 2.7) │        │                              │
│                              │        │  serve.py  — сервер для окна │
│  ┌────────────────────────┐  │  HTTP  │  chat.py   — ход разговора   │
│  │  ИИ-мост (My Commands) │◄─┼────────┼─ tools.py  — инструменты     │
│  │  главный поток → API   │  │  JSON  │  rpro_client.py, llm_ollama  │
│  └────────────────────────┘  │        └───────────┬──────────────────┘
│  ┌────────────────────────┐  │                    │ HTTP
│  │  Плагин C#             │  │  HTTP              ▼
│  │  тикер + окно чата     │──┼────────┐ ┌──────────────────────────────┐
│  └────────────────────────┘  │        └▶│   Ollama (локальные модели)  │
└──────────────────────────────┘          │  чат-модель + модель зрения  │
        ▲ снимок окна средствами Windows   └──────────────────────────────┘
```

Разделение ответственности:

- **внутри R-Pro** — только тонкий мост: очередь, HTTP, вызовы Python-API. Никаких
  обращений к моделям, никакой бизнес-логики;
- **снаружи** — всё остальное: работа с моделью, инструменты, история диалога.

Почему так: встроенный Python — версия 2.7, современные библиотеки туда не встают.
К тому же падение внешнего процесса не роняет программу, в которой инженер работает.

## Почему агент вообще «видит» происходящее

Три независимых источника, которые дополняют друг друга:

1. **Структура сцены через API** — точные имена, координаты, свойства, сообщения
   программы. Это основной канал: он даёт факты, а не догадки.
2. **Снимок окна программы** средствами Windows — картинка того, что видит
   пользователь: 3D-вид, дерево компонентов, лента, панель вывода. Её смотрит
   модель со зрением и описывает словами. Штатный снимок 3D-вида через
   Python-API в этой сборке не работает, подробности в
   [05-problema-tika.md](05-problema-tika.md).
3. **(Задел на будущее) дерево интерфейса через UI Automation** — состояние панелей
   и диалогов в виде текста, а не картинки. Понадобится, когда агент начнёт
   подсказывать по интерфейсу: «нажмите вот эту кнопку на ленте».

## Этапы

### Фаза 1 — мост и агент в терминале (сделано в этом выпуске)

- мост в `My Commands`, HTTP на `127.0.0.1:8765`;
- десять инструментов: состояние, сцена, поиск, компонент, сообщения, симуляция,
  выделение, изменение свойства, взгляд на вид, выполнение Python;
- диалог в терминале рядом с открытой R-Pro;
- самопроверка связки (`selfcheck.py`).

Это уже рабочий сценарий «параллельной работы»: инженер в программе, агент в соседнем окне.

### Фаза 3 — окно чата внутри R-Pro (сделано)

Плагин на C# (`addon/`) даёт две вещи:

* **тикер** — заставляет программу рисовать кадры через штатную службу
  `IRenderService`, без чего мост не получает управления. Это оказалось нужно
  раньше плана: см. [05-problema-tika.md](05-problema-tika.md);
* **панель «ИИ-агент»** — пристыкованное справа окно переписки.

Панель намеренно тонкая: рисует переписку и отправляет вопросы серверу агента
(`agent/serve.py`), а вся работа с моделью, инструментами и историей остаётся в
Python. Причина та же, что и у моста: внутри R-Pro живёт Python 2.7, современные
библиотеки туда не поставить, а падение внешнего процесса не должно мешать
инженеру работать.

Устройство повторяет штатные панели R-Pro: наследник `DockableScreen` с
экспортом `IDockableScreen` — ровно так сделаны каталог и редактор компонентов.
Разметка разбирается во время выполнения, потому что сборка идёт компилятором
из состава .NET Framework, а тот не умеет компилировать XAML.

### Фаза 2 — MCP-сервер (отложена)

Обёртка тех же инструментов в протокол MCP. Даёт подключение агента к Claude Code,
Claude Desktop и другим клиентам без собственного интерфейса чата, а также
общий доступ для 3–4 человек к одному контуру.

Добавляется: чтение `.rpro` без запуска программы, работа с каталогом компонентов,
сценарии «собери ячейку по описанию».

Порядок фаз поменялся по ходу дела: окно чата сделали раньше MCP-сервера, потому
что оно нагляднее показывает результат, а плагин на C# всё равно пришлось освоить
ради тикера.

## Требования, которые заданы условиями работы

- **Только локальный контур.** Никаких облачных моделей: всё через Ollama на рабочем
  сервере. Данные проектов не покидают сеть предприятия.
- **Мост слушает только `127.0.0.1`.** Наружу порт не смотрит. Для доступа с другой
  машины предполагается SSH-туннель, а не открытый порт.
- **Инструмент `rpro_exec` выполняет произвольный код.** Это осознанный компромисс
  ради гибкости: он отключается одной настройкой (`allow_exec` в `bridge.json`),
  а на случай сетевого доступа предусмотрен токен.

## Перенос на серверные модели

Сейчас модели крутятся на рабочей станции разработчика. Когда появятся новые серверы,
меняется ровно одна переменная окружения:

```
OLLAMA_URL=http://<адрес-сервера>:11434
```

Всё остальное — мост, инструменты, диалог — остаётся без изменений.
