# Проблема тика: как мост получает управление

**Решена.** Кадры обеспечивает плагин на C# (папка `addon`). Ниже — в чём была
суть и почему все попытки решить её изнутри Python провалились. Это не история
ради истории: если кто-то возьмётся «упростить» конструкцию, здесь написано,
какие упрощения уже проверены и чем закончились.

## Суть

Python-API R-Pro можно трогать только из главного потока приложения. Значит,
мосту нужен «тик» — момент, когда R-Pro сама передаёт управление нашему коду.
Единственное живое событие — `OnRender`, а рисует программа **по необходимости**:
пока пользователь работает, кадры идут; убрал руки — тишина, и мост немеет.

## Что перепробовано и почему не подошло

| Способ | Итог |
|--------|------|
| Фоновый поток с HTTP-сервером | интерпретатор удерживает GIL, пока не выполняет свой код; поток не получает управления. Соединение при этом принимает ядро ОС, поэтому снаружи выглядит как работающий сервер |
| Таймер Windows (`SetTimer` + колбэк через `ctypes`) | **вешает программу насмерть** (`AppHangB1` в журнале Windows) |
| Событие `OnIdle` | не срабатывает ни разу; в справке помечено устаревшим, и это буквально |
| Цепочка «кадр просит следующий» | живёт ровно один шаг: `Simulation.World.update()` даёт один кадр, дальше миру нечего обновлять |
| Перерисовка окна, виртуальная мышь, `SetWindowPos`, `PrintWindow` | не действуют: 3D-вид рисуется средствами WPF внутри единственного окна, своего окна у него нет |
| Потоковая передача анимации (порт 7000) | упирается в лицензию: в коде рядом лежит «License does not include animation streaming» |

## Ловушка, на которой я потерял день

Перебор способов вызвать кадр (`agent/tickhunt.py`) сначала объявил рабочими
почти все — включая подстройку свойства `AmbientOcclusionContrast`, которого в
этой сборке **вообще не существует**. Разгадка простая: замеры шли, пока
пользователь водил мышью, и рост счётчика кадров давала мышь, а не проверяемый
способ.

Отсюда правило на будущее: **измеряя автономность, проверяй, что источник помех
выключен**. Курсор можно опросить через `GetCursorPos` и убедиться, что он
неподвижен; событие в логе стоит сверять со временем и паузами между кадрами.

## Решение

У платформы .NET есть штатная служба отрисовки `IRenderService` с методом
`RequestRender()`. Из Python она недоступна — в этом и была причина полутора
дней мучений.

Плагин `addon/AiBridgeTicker.cs` (около 50 строк) получает эту службу и по
таймеру WPF просит кадр десять раз в секунду. Конструкция не выдумана: ровно так
устроен штатный плагин R-Pro `AutosaveAgent` — тот же интерфейс `IPlugin`, тот же
`ImportingConstructor` со службой отрисовки, тот же `DispatcherTimer`.

Проверено на живой программе: мост отвечает за **0,09 с** без единого касания
мыши, отрисовка держится на **5,5 кадра в секунду** при полном бездействии.

## Побочные находки

**Ошибка, маскировавшаяся под отсутствие тика.** Ответы моста рушились о
`UnicodeDecodeError`: в трассировках и сообщениях R-Pro попадаются строки в
cp1251. Запросы доходили до обработчиков, но клиент не получал ничего. Исправлено
в 0.4.1, разбор кодировок покрыт офлайн-проверкой.

**Снимок 3D-вида через API не работает.** `beginFrameGrab` отрабатывает без
ошибок, но файла не создаёт ни при каком написании пути, а `saveBitmap` и
`saveScreen` из справки в модуль `vcCommand` не выставлены вовсе. Снимок делается
снаружи средствами Windows (`agent/capture.ps1`), и это оказалось даже полезнее:
в кадр попадает всё окно программы, а не только сцена.

**Очередь подключений.** У спящего моста накапливаются неотвеченные соединения,
и новое подключение виснет по таймауту. Отличать «программа не запущена» нужно по
отказу в подключении, а не по таймауту.
