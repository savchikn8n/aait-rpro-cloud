# Протокол моста

Мост поднимает HTTP-сервер внутри процесса R-Pro. По умолчанию — `http://127.0.0.1:8765`.

## Формат запроса

Любой `POST` на корень сервера с телом в JSON:

```json
{
  "method": "scene",
  "params": { "limit": 50 },
  "timeout": 30
}
```

Ответ всегда со статусом `200` и телом:

```json
{ "ok": true,  "result": { } }
{ "ok": false, "error": "текст ошибки или трассировка" }
```

Если в `bridge.json` задан `token`, к запросу добавляется заголовок `X-Bridge-Token`.

Отдельно есть `GET /health` — он не обращается к API R-Pro и отвечает, даже когда
главный поток занят. Полезен, чтобы отличить «мост не запущен» от «R-Pro задумалась».

## Методы

| Метод | Параметры | Что возвращает |
|-------|-----------|----------------|
| `ping` | — | версия моста, версия продукта, счётчики запросов и прокачек очереди |
| `status` | — | открытый проект, режим, число компонентов, состояние симуляции, выделение |
| `scene` | `limit`, `with_position` | список компонентов с координатами в мировой системе |
| `find` | `query`, `limit` | компоненты, в имени которых есть подстрока |
| `component` | `name`, `with_properties`, `with_behaviours`, `with_children` | подробности компонента |
| `set_property` | `component`, `property`, `value` | новое значение свойства |
| `select` | `names` | какие компоненты выделены после вызова |
| `messages` | `tail`, `clear` | последние строки панели вывода |
| `simulation` | `action` (`status`/`run`/`run_for`/`run_until`/`halt`/`reset`), `seconds` для `run_for`, `until` для `run_until` | состояние симуляции; запуски идут в реальном времени и не ждут остановки. `run_until` на отметку раньше текущей — перемотка назад: сброс и прогон с нуля. `reset` после сброса делает служебный прогон на 1 мс и второй сброс, иначе часы на панели не обнуляются |
| `screenshot` | `width`, `height`, `path`, `as_base64` | путь к PNG и, по желанию, сама картинка в base64 |
| `exec` | `code` | `stdout`, `stderr` и значение переменной `result` |
| `layout` | `action` (`open`/`save`/`clear`/`load_component`), `uri` | результат операции |
| `help` | — | список доступных методов |

## Как устроено выполнение

1. HTTP-поток принимает запрос и кладёт задание в очередь. **Сам он Python-API R-Pro не трогает** —
   это привело бы к падению программы.
2. Тот же поток будит цикл сообщений Windows пустым сообщением (`PostMessage` через `ctypes`).
3. Главный поток на событии `OnIdle` или `OnRender` разбирает очередь и выполняет задание.
4. HTTP-поток дожидается результата и отвечает клиенту.

Из этого следуют два практических правила:

- пока в R-Pro открыт **модальный диалог**, очередь не разбирается, и запросы отваливаются
  по таймауту — это нормальное поведение, а не поломка;
- запрос стоит считать «медленным вызовом»: типичное время ответа десятки миллисекунд,
  но снимок вида занимает заметно дольше.

## Примеры

PowerShell:

```powershell
Invoke-RestMethod http://127.0.0.1:8765/health

Invoke-RestMethod -Method Post http://127.0.0.1:8765 -ContentType 'application/json' -Body '{"method":"status"}'
```

Python 3:

```python
from rpro_client import RProClient

client = RProClient()
print(client.status())
print(client.find("Robot"))
print(client.exec_python("result = [c.Name for c in app.Components]"))
```

## Коды ошибок

Отдельных числовых кодов нет: в поле `error` приходит текст. Частые случаи:

| Текст | Причина |
|-------|---------|
| `Мост недоступен по адресу …` | R-Pro не запущена или мост не установлен |
| `R-Pro не обработала запрос за N с` | открыт модальный диалог либо идёт тяжёлая операция |
| `неизвестный метод: …` | опечатка в имени метода, полный список даёт `help` |
| `компонент "…" не найден` | имя чувствительно к регистру, проверьте через `find` |
| `не удалось занять порт …` | уже открыто второе окно R-Pro с мостом |

## Совместимость версий

Версия моста хранится в `BRIDGE_VERSION` (`bridge_command.py`) и возвращается в `ping`
и `/health`. При несовместимых изменениях протокола версия повышается, а в README
описывается порядок обновления.
